# تقرير مراجعة MVP0 — Gazabella

تاريخ المراجعة: 25 سبتمبر 2026.

> هذا تقرير خط الأساس قبل الإصلاحات. نتائج التنفيذ اللاحقة واختبار تجربة المستخدم موثقة في [تقرير 26 سبتمبر](MVP0_IMPLEMENTATION_2026-09-26_AR.md).

## الحكم

**MVP0 غير مكتمل ولا تتوفر أدلة كافية لإغلاقه.** يوجد أساس Backend كبير وواجهة عميل متقدمة، لكن عقد الاتصال بينهما غير موحد، والحجز والدفع وبعض قواعد البيانات لا تطابق المرجع. وجود الشاشة أو نجاح الاختبار المحلي لا يعني اكتمال الوظيفة من الواجهة إلى الخادم.

## نطاق المراجعة وحدودها

- المرجع المطلوب: `Docs/gazabella_mvp 0 + 1 + 2+ 3.html`، خصوصًا تبويب «MVP 0 المعتمد» الذي يبدأ قرب السطر 5516، مع قراءة حدود MVP1 لتحديد المؤجل.
- الفرونت إند: نسخة العمل الحالية في `C:/Users/HP/Desktop/Gazabella-Front`، بما فيها التعديلات غير الملتزم بها في Git.
- الباك إند: عُثر على نسخة محلية في `C:/Users/HP/Desktop/GazabellaOnlineStore/backend` وتمت قراءة كودها. **لم يثبت أنها النسخة المنشورة أو أحدث نسخة لدى عاصم.** نتائج الباك إند أدناه تخص هذه النسخة.
- لم أغير كود التطبيق أو عقد OpenAPI، ولم أنشئ طلبًا تجاريًا أو دفعة، ولم أنفذ migrations على قاعدة تشغيلية.
- لم تُجرَ تجربة متصفح كاملة أو اختبارات تكامل على الخادم المنشور في هذه المراجعة.

## ثانيًا: عوائق إغلاق MVP0

### 1. توحيد العقد بين الفرونت والباك — أولوية قصوى مشتركة

النسختان لا تتحدثان العقد نفسه، رغم وجود اختبارات ناجحة لكل بعض أجزائهما:

| العملية | الفرونت الحالي | Backend المحلي / مرجع MVP0 | الأثر |
|---|---|---|---|
| التحقق من OTP | يرسل `code` | ينتظر `otp` | رفض validation |
| صيغة الهاتف | يقبل الرقم المحلي أو 970/972 ويرسله دون توحيد | يقبل `+970` ثم 9 أرقام | الرقم المحلي المعروض مثالًا في الواجهة يُرفض |
| استجابة OTP | يقرأ `data.data` قبل normalizeAuth | يعيد token/user مباشرة | فشل اعتماد الجلسة حتى إذا نجح تحقق الخادم |
| سلة الضيف | `X-Cart-Token` وتهيئة GET /cart | `X-Guest-UUID` وPOST /auth/guest/init | عدم توافق الهوية والدمج |
| إضافة عنصر | POST /cart/items مع product_id | POST /cart مع product_variant_id | مسار وحقل مختلفان |
| تعديل/حذف عنصر | /cart/items/{id} | /cart/{id} | اختلاف المسار |
| إنشاء الطلب | POST /checkout وعنوان نصي | POST /orders وعنوان مركب وdelivery_option_id | مسار وبنية مختلفان |
| التحقق من الجلسة | GET /auth/me قبل عرض الطلبات | غير مسجل في routes/api.php | تعطل وصول الواجهة لصفحات الطلبات مع هذه النسخة |
| سجل الطلبات | normalizeOrder يشترط items وsubtotal ورسوم التوصيل | قائمة مختصرة لا تعيد هذه الحقول | رفض استجابة قائمة صحيحة بحسب التنفيذ المحلي |
| عنوان تفاصيل الطلب | يحتفظ به فقط إذا كان string | Backend يعيد object | اختفاء العنوان في واجهة التفاصيل |

الدليل: `src/api/gazabella.ts` و`src/lib/apiClient.ts` و`src/App.tsx`، مقابل `backend/routes/api.php` وAuthController وOrderController. بعض المسارات الإضافية في الفرونت مثل settings وwishlist ليست في هذه النسخة المحلية أيضًا؛ قد تخص Backend آخر ويجب تثبيت مرجعيته.

**المطلوب:** تحديد نسخة Backend المعتمدة، ثم اعتماد عقد واحد وfixtures فعلية له. اختبارات adapter الحالية تثبت توافق الفرونت مع الاستجابات المصطنعة التي تكتبها الاختبارات، ولا تثبت توافقه مع هذا الباك إند.

### 2. إكمال الحجز وسلامة المخزون — أولوية قصوى

- `php artisan schedule:list` أعاد: **No scheduled tasks have been defined**. توجد جدولة داخل App/Console/Kernel.php، لكنها غير فعالة في التطبيق الحالي. يلزم ربطها فعليًا وتشغيل scheduler في بيئة النشر.
- `reserve()` و`checkoutBegin()` ما زالا يعيدان `reserved_until` في المستوى الأعلى؛ المرجع يفرض `expires_at` وحده. heartbeat يعيد expires_at، أي أن العقد غير موحد حتى داخل Backend.
- `useProceedToCheckout` ينفذ Promise.resolve ثم انتقالًا فقط؛ لا يستدعي reserve أو checkout/begin. وجود useReservationTimer ليس دليلًا على حجز فعلي.
- `OrderService::createOrder` لا يرفض العناصر التي لا تملك حجزًا نشطًا؛ خصم المخزون مشروط بوجود reservation. لذلك يلزم منع إنشاء طلب غير محجوز، وإعادة فحص الصلاحية والكمية والمخزون داخل transaction قبل تثبيت الطلب.
- واجهة API لا تطبق سقف 10 وحدات، بينما Backend يفرضه. السقف في الواجهة مطبق في mock فقط.

**معيار الإنجاز:** حجز ثم تمديد واحد فقط، heartbeat لا يغير الصلاحية، انتهاء الحجز يعيد المخزون، ومحاولات الطلب المتزامنة لا تبيع مخزونًا غير متاح.

### 3. إصلاح دورة Checkout — أولوية قصوى للتكامل

`src/pages/CheckoutPage.tsx` يسمح حاليًا بتأكيد الطلب في وضع API ويعرض «رسوم التوصيل: لم تُحدد بعد». هذا يخالف وصف README القديم الذي يقول إن التأكيد موقوف.

المطلوب قبل اعتبار تدفق العميل جاهزًا:

- عرض خيارات التوصيل والرسوم والخصم والإجمالي المعتمد من الخادم قبل التأكيد.
- استخدام العنوان الهجين: full_name وphone وcity وarea وdetails، مع الحقول الاختيارية المتفق عليها.
- إضافة active_cities إلى config والتحقق منه؛ النسخة المحلية تقبل city كنص فقط ولا تحتوي الإعداد المذكور في الوثيقة.
- تحديد مسار العميل الضيف: Backend المحلي يشترط Sanctum للطلبات، بينما صفحة Checkout غير محمية؛ توحيد قرار الدخول والدمج قبل الإتمام.
- توحيد order_number في روابط الطلبات؛ صفحة Checkout تستخدمه، لكن صفحة قائمة الطلبات تتبع تمييزًا آخر بين mock وAPI، والتعليقات والأنواع تفترض معرفًا رقميًا في API.
- منع تكرار الطلب على الخادم عند إعادة المحاولة بعد انقطاع الشبكة؛ تعطيل الزر أثناء الإرسال لا يكفي.

### 4. ضبط الدفع وحالات الطلب — أولوية قصوى للـBackend

- يوجد init وwebhook للدفع وSandbox URL، لكن هذه ليست شهادة نجاح تكامل Jawwal Pay.
- PaymentService يكتب حالة الطلب `paid` عند نجاح webhook، بينما migration الجديدة لا تسمح بهذه الحالة وتستخدم `confirmed` بدلًا منها. يجب فصل حالة الدفع عن حالة الطلب وتوحيدهما مع العقد، ثم اختبار MySQL.
- verifyWebhookSignature يسمح بالمرور إذا كان secret فارغًا حتى خارج Sandbox؛ يجب أن يرفض الإعداد الناقص خارج الاختبار.
- الفرونت يحتوي confirmJawwalPayment وlookupOrderByReference لمسارات غير موجودة في النسخة المحلية، بينما initPayment الحقيقي يعيد «الخدمة غير متاحة». ليست هناك رحلة دفع Sandbox موصولة من البداية للنهاية.
- الواجهة ترسل `payment_method: cod`، لكن إنشاء الطلب المحلي لا يعالج هذا الحقل ويعيد next_step إلى payments/init؛ دعم COD يحتاج اعتمادًا وتنفيذًا صريحًا في الطرفين.
- يجب تأكيد تطبيق ENUM migrations على MySQL في الخادم؛ لم تُنفذ migrations تشغيلية ضمن هذه المراجعة.

### 5. تصحيح الاختبارات والتوثيق

- الوثيقة تعرض «49 Tests Passed» ثم 46 ناجحًا و5 skipped وفشلين، وتشرح skipped بأنها 4؛ لا يمكن اعتماد هذه الأرقام كحالة حالية.
- SecurityTest يتوقع 201 لإضافة السلة ثم يتخطى اختبار عزل الضيوف إذا تغيرت الحالة، مع أن الحالة المعتمدة أصبحت 200؛ هذا تخطٍّ يخفي اختبارًا مطلوبًا.
- بعض اختبارات الطلب تقبل نجاحًا أو رفضًا معًا، واختبار ملكية الطلب يستخدم رقمًا وهميًا دون إنشاء طلب فعلي للمستخدم الآخر. يجب تقويتها لإثبات السيناريو المقصود.
- README وAPI_REVIEW_AR وFRONTEND_MVP0_HANDOFF تصف مراحل مختلفة؛ مثال ذلك OTP وفتح Checkout. يجب تحديثها بعد تثبيت العقد.

## ثالثًا: ما يُرحّل إلى MVP1 وفق قراءة الوثيقة

الوثيقة نفسها تقول إن MVP1 يكمل Pending، وأن Backend هو أساس MVP0 وربط الواجهات الكامل والدفع الفعلي يأتيان في MVP1. لذلك لا ينبغي خلط إغلاق الأساس مع إنجاز كل الإطلاق التجاري.

| الميزة | الحالة المحلية | المرحلة المقترحة بحسب الوثيقة |
|---|---|---|
| Store/Delivery APIs وGuards | غير موجودة؛ auth.php يضم web وsanctum وadmin فقط | MVP1 |
| Escrow وDispute وSettlement | لا تنفيذ مالي حقيقي؛ البلاغ mock | MVP1 |
| PIN تأكيد التسليم | محاكاة محلية وعرض حقل إن وصل | MVP1 |
| Rating وKYC | لا Models/API تشغيلية في النسخة المحلية | MVP1 |
| FX snapshot والتسويات الأسبوعية | غير موجودة في خدمة الطلب المحلية | MVP1 |
| SMS fallback وAcceptance Timeout | غير منفذة محليًا؛ إرسال OTP الفعلي نفسه ما زال TODO | MVP1/متطلبات الإطلاق |
| Jawwal Pay Production | غير متحقق؛ Sandbox غير موصول كاملًا | Production في MVP1؛ إصلاح تناقضات الأساس في MVP0 |
| Reverb الفعلي | أحداث Backend موجودة؛ hook الفرونت غير مستدعى، واسم القناة والحدث مختلفان | استكماله ضمن تكامل MVP1 إذا اعتُمد هذا الحد |

تفصيل Reverb: Backend يبث `orders.{userId}` و`order.status_changed`، بينما hook الفرونت يتوقع `App.Models.User.{id}` و`order.status.updated`. لا يكفي وضع مفتاح Reverb في البيئة لتشغيله. يلزم أيضًا ضبط Bearer لمصادقة القنوات والتحقق من ملكية قنوات الضيف.

**استثناء من التأجيل:** تنظيف الحجوزات وسلامة المخزون وتناسق حالات الدفع ليست تحسينات مستقبلية؛ تعطل الأساس نفسه، ولذلك يجب إغلاقها في MVP0 حتى لو ورد التنظيف ضمن قائمة MVP1 بأولوية منخفضة.

## رابعًا: ترتيب التنفيذ ومعايير إغلاق المرحلة

1. **أشرف + عاصم:** تثبيت Backend المعتمد وعقد API وحدود MVP0 كتابةً، وحسم الاختلاف مع النسخة المستخدمة حاليًا في الفرونت.
2. **عاصم:** إصلاح الحجز والمخزون والجدولة وحالات الدفع وتوقيع webhook والعنوان ونطاق المدن، ومعالجة اختبارات الفشل والتخطي غير المبرر.
3. **أشرف:** مواءمة OTP وهوية السلة وvariants وتنسيق الطلبات مع العقد المعتمد؛ إكمال Checkout إذا أُدرج الربط ضمن معيار تسليم MVP0، وإلا تسجيله بوضوح ضمن MVP1.
4. **مشترك:** اختبار SQLite للمنطق وMySQL للمهاجرات وENUM والتزامن، ثم سيناريو متكامل على staging: دخول ← سلة ← حجز ← توصيل/خصم ← طلب ← دفع Sandbox/COD ← تفاصيل الطلب.
5. **مشترك:** توثيق النتائج الحالية وتاريخها، وإغلاق MVP0 فقط بعد زوال العوائق الأساسية، مع قائمة صريحة بما انتقل إلى MVP1.

لا أضع نسبة إنجاز رقمية؛ لا يوجد وزن معتمد للمتطلبات، وبعض ادعاءات الاكتمال تاريخية وبعض الوظائف محاكاة. الوصف الأدق: **الأساس مبني جزئيًا بدرجة جيدة، لكنه يحتاج جولة تصحيح وتوحيد عقد قبل إغلاق MVP0.**

## نتائج التحقق

- `npm run build`: ناجح.
- `npm run lint`: ناجح.
- `npm test`: **31 ناجحًا، 0 فشل، 0 تخطٍّ**؛ اختبارات محلية للفرونت والمحاكاة.
- `php artisan schedule:list`: **لا توجد مهام مجدولة**.
- `php artisan test --no-coverage` على SQLite داخل الذاكرة: **46 ناجحًا، فشلان، 5 متخطاة، 227 assertion**. هذه نتيجة أُعيد إنتاجها في هذه المراجعة وليست نقلًا من الوثيقة.
- الفشل الأول: `checkout begin requires items in cart`، عند `tests/Feature/OrderFlowTest.php:80`؛ الخادم يعيد 409 للسلة الفارغة والاختبار يتوقع 400 أو 422. يلزم توحيد القرار مع العقد؛ لا يعني هذا وحده أن الخادم سمح بسلة فارغة.
- الفشل الثاني: `checkout begin with cart items reserves stock`، عند `tests/Feature/OrderFlowTest.php:106`؛ الاستجابة 409 بينما الاختبار يقبل 200 أو 422. يلزم التحقق من تهيئة السلة والهوية والحجز ثم فرض نتيجة نجاح واضحة، لا مجرد إضافة 409 إلى القيم المقبولة.
- الاختبارات المتخطاة: اثنان لغياب `/auth/me`، واحد لغياب variant غير نشط في بيانات الاختبار، واحد لعزل سلال الضيوف بسبب توقع 201 القديم، وواحد لغياب `/delivery-options`. إذن تفسير الوثيقة بأنها اختبارات Store/Delivery مؤجلة لا يطابق التشغيل الحالي.
- نجاح اختبارات OTP يستخدم Redis mock؛ لا يثبت إرسال SMS فعليًا. واختبار SQLite لا يثبت سلامة ENUM على MySQL.
