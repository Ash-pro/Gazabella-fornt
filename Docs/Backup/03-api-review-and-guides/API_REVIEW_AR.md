# مراجعة Gazabella وربط API — 2026-09-24

## النتيجة وحدود التسليم

تم إصلاح الأعطال المكتشفة في البناء وتدفق المتجر، وربط البيانات العامة والمفضلة والسلة بمصدر API، مع إبقاء العرض التجريبي اختيارًا صريحًا. هذه مراجعة للكود المتاح والعقد المرفق وفحوص تشغيل محددة؛ ليست شهادة بخلو جميع الحالات من الأخطاء أو اعتماد إطلاق إنتاجي.

**إتمام الطلب الحقيقي متوقف عمدًا في الواجهة وطبقة الخدمة** إلى حين توفير تسعير نهائي قبل إنشاء الطلب. لا يجوز عرض رسوم شحن مجانية أو نجاح دفع أو OTP غير موجود في الباك إند. تبقى السلة قابلة للاستخدام. لا تطلب الصفحة بيانات شخصية ما دام التأكيد غير متاح.

الملف المرفق يتضمن 25 عملية. عملية health فقط تحتوي schema للاستجابة، بينما 24 عملية تكتفي بوصف نصي. الجرد الآلي الكامل في `API_ENDPOINT_INVENTORY.json`. لذلك أنواع المصادقة والطلبات ليست عقدًا موثقًا نهائيًا؛ يلزم تأكيدها بعينات من بيئة اختبار وحساب عميل.

- ربط عنوان الموقع والوصف وبيانات الاتصال من settings، والبانرات من banners، والمجموعات من collections. إزالة الإعلان الثابت عن تغطية جميع غزة والعرض الثابت لتصنيف bridal غير الموجود في الخادم الحالي.
- تحويل site_name/support_email/support_phone/social وcta_text/cta_url إلى نموذج واجهة ثابت.
- معالجة children المفقودة، وجلب صفحات التصنيفات والعلامات والمفضلة بالكامل.
- إصلاح قيم الترتيب لتوافق price/-price/-created_at؛ إلغاء «الأكثر طلبًا» لعدم توثيق معيار له.
- اختيار تصنيف واحد بما يوافق category_id المفرد، ومنع تحميل نتائج جميع المنتجات أثناء انتظار معرفة معرف التصنيف.
- ربط المفضلة بالمستخدم والخادم مع طلب تسجيل الدخول للضيف، ومنع إعلان النجاح قبل إتمام العملية. تعطيل فلاتر نتائج المتجر داخل المفضلة حتى لا تظهر خيارات لا تنفذ عليها.
- إضافة صفحات سجل الطلبات والتحقق من الجلسة قبل دخول صفحات الطلبات.
- إلغاء الاستعلامات وتنظيف الذاكرة المؤقتة عند تغير الحساب، وفصل مفاتيح الجلسة حسب مصدر البيانات والخادم. قد يحتاج المستخدم إلى تسجيل الدخول مجددًا بعد التحديث.
- تثبيت هوية سلة الضيف قبل الإضافة ومشاركة طلب تهيئتها بين المستدعين المتزامنين؛ حفظ التوكن الوارد في الجسم أو الهيدر.
- إصلاح السعر الأصلي في سلة التخفيضات، والحفاظ على صور CDN بدل استبدال كل النطاقات بنطاق التخزين.
- عدم اعتبار 401 لطلب قديم إلغاءً لجلسة أحدث، وعدم مسح سلة الضيف عند انتهاء جلسة العميل.
- عدم اختراع رسوم توصيل صفرية أو حالة «غير مدفوع» عندما تغيب بيانات الطلب؛ المبالغ غير المكتملة تسبب رسالة خطأ.
- إزالة ادعاءات حجز المخزون والعداد وخدمة الأحداث غير الموثقة من المسار الفعلي.
- تحسين عناوين الحقول ورسائل الأخطاء وتخطيط بانرات الجوال، ومعالجة رفض تثبيت PWA دون إعادة استخدام prompt مستهلك.
- إصلاح مخزون وسعر الخصم في المحاكاة، ورفض دفع إلكتروني لطلب تجريبي نقدي.

## مراجعة جميع مجموعات API

| العمليات | النتيجة والإجراء |
|---|---|
| GET /api/status | health موثق؛ لا حاجة لاستدعائه مع كل تحميل للمتجر |
| POST /auth/register، POST /auth/login | الحقول مطابقة للعقد؛ تحقق من وجود token/user قبل اعتماد الجلسة؛ الاستجابة المباشرة والمغلفة مدعومتان، لكن يلزم fixture معتمد |
| GET /auth/me، POST /auth/logout | موصولتان؛ me يحمي صفحات الطلبات، وlogout ينظف الجلسة بعد نجاح الخادم |
| GET /home | تمت قراءة الاستجابة المجمعة؛ الواجهة تستخدم حاليًا الموارد المنفصلة لتشارك cache بين الهيدر والمتجر. لا يلزم استدعاء النسختين |
| GET /settings | تحقق حي وتحويل أسماء الحقول الفعلية |
| GET /banners | تحقق حي؛ CTA إلى /products و/categories/:slug يحوّل لمسارات الواجهة؛ روابط غير آمنة لا تعرض |
| GET /collections | تحقق حي وربط collection_id في المنتجات |
| GET /categories، GET /categories/{slug} | مراجعة العقد؛ قائمة التصنيفات مستخدمة، ولا توجد صفحة مستقلة تحتاج استدعاء تفاصيل التصنيف |
| GET /brands، GET /brands/{slug} | مراجعة العقد؛ قائمة العلامات متاحة في طبقة الخدمة. لا توجد صفحة علامات مستقلة في التصميم الحالي |
| GET /products، GET /products/{slug} | قائمة وتفاصيل وبحث وتصنيف وأسعار وترتيب وصفحات؛ ترميز slug في المسار |
| GET /cart، DELETE /cart | جلب وتحويل الهوية والتفاصيل؛ الحذف متاح بطبقة الخدمة |
| POST /cart/items، PATCH /cart/items/{item}، DELETE /cart/items/{item} | موصولة؛ اختبار إضافة وحذف حي على سلة ضيف، واختبارات adapter للتنسيق والهوية |
| POST /checkout | العقد يذكر cash on delivery فقط؛ موقوف حتى عقد عرض السعر وعدم تكرار الطلب |
| GET /orders، GET /orders/{order} | موصولتان؛ صفحات ومعرف رقمي في وضع API. اختبار العقد محلي؛ تحتاجان تحققًا حيًا بحساب اختبار |
| GET /wishlist، POST /wishlist/{product} | موصولتان بواجهة المفضلة؛ pagination متبوع، toggle يستخدم slug؛ تحتاجان تحققًا حيًا بحساب اختبار |

جميع المسارات السابقة عدا status تقع تحت /api/v1. لا توجد خدمات Merchant/Delivery/Payment/OTP/Coupon/Reservation/Dispute في المرفق.

## متطلبات الباك إند بالترتيب

### P0 — عرض السعر قبل التأكيد

توفير خدمة preview/quote تستقبل عنوان التوصيل وهوية السلة، وتعيد subtotal وdelivery_fee وdiscount وtotal وcurrency، وخيارات التوصيل المتاحة والسبب عند عدم التغطية، وquote_id/expiry/cart_version. يقبل checkout مرجع العرض ويتحقق من الأسعار والمخزون والتغيرات قبل الإنشاء. عند التغير يجب إعادة المراجعة، لا مفاجأة العميل بعد إنشاء الطلب. لم أضف endpoint افتراضيًا أو سعرًا ثابتًا للواجهة.

### P0 — منع تكرار الطلب واسترجاع النتيجة

توثيق Idempotency-Key للـcheckout وكيفية استرجاع الطلب بعد timeout؛ إعادة المحاولة بنفس المفتاح تعيد الطلب نفسه. عدم تشغيل retry تلقائي لعمليات الكتابة موجود في الواجهة، لكنه لا يحل مشكلة انقطاع الشبكة بعد وصول الطلب للخادم.

### P0 — استكمال عقد الاستجابات

إضافة schemas وexamples وnullable/enums والأخطاء لـ24 عملية، وبالأخص auth/cart/order/wishlist toggle. تحديد money types/currency ووحدات المخزون، وبنية عنوان الطلب، وما إذا كانت قائمة الطلبات تحتوي items أو ملخصًا فقط. الواجهة ترفض المبالغ الناقصة بدل افتراضها صفرًا.

### P0 — العميل الضيف واستمرارية السلة

checkout يقبل الضيف بينما قراءة الطلب محمية بـSanctum. يلزم قرار وعقد صريح: إما اشتراط حساب قبل الإنشاء مع دمج آمن للسلة، أو رابط تتبع ضيف بتوكن محدود النطاق والمدة. يجب توثيق دمج سلة الضيف عند التسجيل/الدخول. لم أرسل X-Cart-Token مع المستخدم المسجل لأن وصف العقد يطلب حذفه للمستخدم المصادق. لا يكفي redirect إلى طلب لا يملك الضيف صلاحية قراءته.

### P1 — الدفع الإلكتروني

إذا كان جوال بي مطلوبًا، توفير initiate/status أو hosted checkout وwebhook موثّق والتحقق من المرجع على الخادم. لا يجمع الفرونت OTP الخاص بمزود الدفع ولا يؤكد الدفع من query parameter. حتى ذلك الوقت المتاح بالعقد نقد عند الاستلام فقط.

### P1 — المحتوى والبيانات الفعلية

رصد حي: إعدادات الدعم ترجع رقمًا شكليًا `+962 79 000 0000`، وروابط الصور تحت `/storage/placeholders/`. في تصنيف perfumes ظهر شبشب عروس وكريم يدين، وأسعار بآلاف الشواكل. هذه أمثلة تحتاج مراجعة المحتوى والتصنيف والتسعير قبل الإطلاق؛ ليست دليلًا أن الفرونت يحسبها خطأ. تظهر البيانات كما أرسلها الخادم.

### P1 — البانرات والروابط

الاستجابة تحتوي type=badge رغم أن وصف المرفق يذكر hero/promo/announcement فقط. اعتماد enum موحد وschema لكل نوع. اعتماد أنواع وجهات CTA داخلية بدل روابط مسارات قد لا يملكها الفرونت، أو نشر جدول موحد للمسارات. تحديد التواريخ والمنطقة الزمنية وقواعد ترتيب البانرات.

### P1 — إعدادات العلامة والتوصيل

توثيق اسم الموقع والشعار والعنوان وروابط التواصل ومناطق الخدمة. لا يجوز وعد العميل بتغطية مدينة أو قطاع كامل من نص ثابت لا يعتمد بيانات تشغيلية.

### P1 — الأدوار والعمليات

لتفعيل لوحات التاجر والمندوب يلزم صلاحيات وخدمات مخزون وتجهيز ومهام وحالات انتقال، مع تحقق server-side من الملكية. إذا كانت الحجوزات أو التسليم بالرمز أو النزاعات مطلوبة، يلزم إضافتها للعقد؛ لا تكفي محاكاة المتصفح.

### P2 — pagination والأخطاء والتحديثات

توثيق page/per_page/max_page_size للمفضلة، بنية pagination الموحدة، rate limits وأخطاء 401/403/404/409/422/429. توثيق سياسة X-Cart-Token وCORS وAccess-Control-Expose-Headers. توثيق قنوات WebSocket ومصادقتها قبل إعادة تشغيلها. تأكيد دلالة فلتر وفرز السعر للمنتج المخفض.

## التحقق وما لم يُختبر

- نجح بناء production وlint، و24 اختبارًا محليًا تغطي عمليات السلة والأسعار والمفضلة والعقد والهوية ومنع fallback وحالات الطلبات التجريبية.
- تمت مراجعة الواجهة في المتصفح بقياس جوال 390×844، بما فيه قائمة التصنيفات ودرج السلة وصفحة تعذر الإتمام؛ ومراجعة سطح المكتب.
- فحص حي للبيانات العامة: products/settings/banners/collections/categories/home وcart. إضافة منتج لسلة ضيف ثم حذفه؛ لم يتم إنشاء طلب أو دفع.
- خدمات المصادقة الناجحة والطلبات الخاصة والمفضلة الخاصة لم تُختبر على حساب حي لعدم توفر حساب اختبار. لا تُعرض اختبارات adapter أو mock على أنها اختبارات تكامل حي لهذه الخدمات.
- اختبارات الحجز والـOTP والمتغيرات القديمة استُبدلت باختبارات العقد الحالي لأنها كانت تشير لدوال حُذفت قبل هذه المراجعة؛ لم تُعد الخدمات المحذوفة اصطناعيًا كي تنجح الاختبارات.
- لم يتم نشر الموقع أو تعديل الباك إند. بقيت تغييرات المستخدم السابقة في مساحة العمل.

## شروط رفع الإيقاف عن Checkout

اعتماد quote + idempotency + تتبع الضيف/دمج السلة + schemas، ثم اختبار staging لنجاح الطلب، نقص المخزون، تغير السعر، رفض التغطية، timeout بعد الإنشاء، إعادة المحاولة، وانتهاء الجلسة. بعد ذلك فقط يُفعّل زر التأكيد وتُعرض الرسوم والإجمالي الموثقان.

## متابعة: تحسين تجربة المصادقة

تم تقديم النموذج في يمين واجهة RTL مع تقليل مساحة الصورة وإخفائها على الجوال، وتوضيح الاختيار النشط، وإضافة إظهار كلمة المرور والتعليمات، وحقل تأكيد كلمة المرور مع التحقق من التطابق قبل الإرسال (ترسل password_confirmation بالقيمة المدخلة في التأكيد). الاسم والبريد ما زالا مطلوبين لأن عقد register يفرضهما. أضيف مسار متابعة التسوق دون التسجيل، وليس وعدًا بإتمام طلب ضيف.

الدخول برقم الجوال **لم يُفعّل**: يلزم إرسال رمز وتحقق منه، صلاحية الرمز، حدود الإرسال والمحاولات، تبريد إعادة الإرسال، توحيد الرقم الدولي، ومنع كشف وجود الحساب. بعد التحقق يصدر الخادم جلسة للحساب القائم أو تسجيلًا آمنًا للحساب الجديد، مع عقد لاستكمال الاسم لاحقًا بدل الاسم الإلزامي الآن. لا يُحوّل رقم الجوال إلى بريد وهمي ولا يستعمل OTP محلي.

استعادة كلمة المرور **غير مدعومة بالعقد**؛ رابط المساعدة في الصفحة يوضح عدم توفر الاستعادة ويعرض وسيلة الدعم من settings إذا توفرت. يلزم endpoint لطلب الاستعادة وآخر للتأكيد بتوكن قصير العمر وحماية من كشف الحسابات. لا يُعرض نجاح إعادة تعيين دون تنفيذ فعلي.
