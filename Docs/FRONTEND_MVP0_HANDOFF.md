# تسليم تحسينات Frontend — MVP 0

مرجع النطاق: آخر تبويب «MVP 0 المعتمد» من Gazabella_artifact_v15. هذا الملف يوثق حالة الفرونت إند ولا يغير قرارات الوثيقة أو عقد OpenAPI.

## ما أصبح متاحًا للعرض

- تصميم موحد للمتجر: مقدمة أقصر، تصنيفات ديناميكية، شبكة منتجات، بحث وتصفية وترتيب وترقيم صفحات.
- صفحات تفاصيل المنتج والنوع والكمية، درج السلة، دخول OTP، Checkout بخطوتين، سجل وتفاصيل الطلبات.
- حالات تحميل وفراغ وخطأ، وصور بديلة محايدة، ودعم RTL والتركيز بلوحة المفاتيح وتقليل الحركة.
- لوحة تاجر تحفظ المخزون لكل نوع وحالة التجهيز محليًا، وإحصاءات مشتقة من بيانات العرض.
- لوحة توصيل تتحقق من تسلسل الحالة والرمز الصحيح في Mock Mode، وتحدّث سجل الطلب.
- نافذة بلاغ تجريبية بعد التسليم خلال 48 ساعة؛ توضح أنها لا ترسل بلاغًا حقيقيًا.
- إعادة محاولة الدفع للطلب الموجود بدل إنشاء طلب جديد بعد فشل فتح بوابة الدفع.
- الصور المستخدمة أصبحت 591,982 بايت بدل 5,718,940 بايت لنسخ JPG، انخفاض 89.6% في حجم هذه الأصول، وليس قياسًا شاملًا لسرعة الموقع.

## حدود العرض

- البيانات والعمليات محلية. PIN والدفع وحجز المخزون والبلاغات محاكاة للعرض وليست تنفيذًا أمنيًا أو ماليًا.
- تُمنع لوحتا التاجر والتوصيل في وضع API إلى حين اعتماد تسجيل الدخول والصلاحيات الخاصة بهما.
- لم يُنفّذ Filament أو KYC أو التسويات أو SMS أو إدارة أموال Escrow.
- لم نضف تغليفًا مدفوعًا أو صانع هدايا أو ميزات توسع خارج النطاق الحالي.
- صور المنتجات والعلامات والأسماء والهواتف تجريبية وتحتاج محتوى كتالوج معتمدًا قبل إطلاق فعلي.
- المحفوظات محلية ومحصورة في نتائج الصفحة الحالية؛ لا يوجد عقد API لمزامنتها بين الأجهزة.
- COD موجود ضمن عينات مهام التوصيل، لكن اختيار COD في Checkout ينتظر اعتماد عقد الدفع؛ تدفق الإتمام الحالي يحاكي Jawwal Pay.
- Rating غير موصول بخدمة حقيقية، وأزيلت التقييمات الثابتة التي كانت تبدو كآراء عملاء.

## نقاط التنسيق مع عاصم قبل وضع API

1. تثبيت عقد Store/Delivery ومساراته وGuards والأدوار؛ المسارات القديمة في adapter لا تعني اعتمادها أو أنها تعمل.
2. اعتماد الدفع: معرّف الطلب المقبول، payment_url، حالات الدفع، Webhook، وIdempotency Key على الخادم. حارس الواجهة لا يمنع وحده التكرار بعد انقطاع الشبكة أو من أجهزة متعددة.
3. تثبيت نوع حقل Order.id؛ التوثيق النهائي يذكر order_number بينما الأنواع المحلية القديمة تفترض رقمًا. روابط العرض تستخدم order_number بالفعل. يلزم اختبار عقد فعلي قبل تغيير الأنواع أو payload.
4. اعتماد expires_at في reserve/heartbeat/checkout. لا ينتج Mock حقلاً بديلًا؛ توجد قراءة توافقية لـ reserved_until لاستجابات العقد القديم حتى يحسم التكامل.
5. اعتماد مصدر active_cities وخيارات التوصيل وأهلية الكوبونات من الخادم. خانيونس هي قيمة العرض الافتراضية؛ رفض المدن والتحقق من الأسعار والمخزون مسؤولية الخادم.
6. اعتماد endpoints لتأكيد PIN والنزاع والتقييم. وظائف demoOperations لا يجب استدعاؤها في وضع API.
7. تأكيد أسماء أحداث Reverb والقنوات وخصوصيتها. توجد إعادة جلب دورية للطلبات النشطة كوسيلة احتياطية، ولم يُختبر اتصال Reverb حي.
8. اختبار جلسة مستخدمين، الدمج مع سلة الضيف، وفشل 401/409/422، ونفاد المخزون، وانتهاء الحجز أثناء الدفع، وانقطاع الشبكة بعد إنشاء الطلب.
9. اعتماد سياسة الدعم والاسترجاع والمحتوى والصور قبل النشر. لا تعرض الواجهة ضمانًا ماليًا غير متصل بخدمة حقيقية.

## التحقق المنفذ

- TypeScript وVite build.
- Oxlint.
- اختبارات Mock تغطي OTP، الأسعار والترقيم، المخزون، انتهاء الحجز والتمديد مرة واحدة، الكوبونات، الدفع المتكرر لنفس الطلب، فصل منتجات المتاجر، حفظ التجهيز، تسلسل التوصيل وPIN ونافذة النزاع.
- فحص يدوي بالمتصفح على سطح المكتب والهاتف: اختيار نوع، درج السلة، OTP، عنوان التوصيل، تطبيق خصم، إنشاء طلب ودفع تجريبي، ظهوره في لوحة التاجر، رفض PIN خاطئ وقبول الصحيح.
- لم يُختبر Backend أو دفع حقيقي أو صلاحيات Store/Delivery حقيقية. لم يُنشر الموقع.

## ملاحظة PWA

تم إصلاح أصل غير موجود في precache، وحصر التخزين في الملفات العامة من نفس المصدر، واستخدام الشبكة أولًا للتنقل. Service Worker يعمل في بناء الإنتاج فقط. يجب اختبار التثبيت والتحديث والعمل دون اتصال على الأجهزة المستهدفة قبل إطلاق فعلي؛ ارفع إصدار الكاش عند تغيير الأصول العامة ذات الأسماء الثابتة.
